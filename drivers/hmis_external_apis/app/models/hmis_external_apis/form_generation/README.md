# Custom assessment form generator

Turns a legacy field-export CSV into one Custom Assessment definition JSON per `form_definition_identifier`, packages them for transfer to production, and publishes them there directly. This is for constructing forms from a vendor export during an initial HMIS migration.

## Scope — what this tool does NOT cover

This only covers **Custom Assessment form definitions generated by this tool** from a legacy CSV export. It does not cover:

- Hand-rolled custom forms (Case Note, Service form(s), etc.) — those are built directly in Form Builder or by hand, not generated.
- Other custom assessment forms that were generated some other way (not via this CSV pipeline).
- Patches automatically applied on deploy to the standard, version-controlled ("managed_in_version_control") HUD forms — those live under `drivers/hmis/lib/form_data/` and are a separate mechanism.

## Workflow

There is no staging step. The initial load is run directly in production, because the dbt migration pipeline expects the CDEDs (CustomDataElementDefinitions) it mints to already exist.

1. **Generate JSON** (wherever you have the legacy CSV — usually your machine):

   ```bash
   dcr shell bundle exec rails driver:hmis_external_apis:generate_custom_assessment_forms CSV_PATH=/path/to/source.csv ZIP=true
   ```

   Writes, under `drivers/hmis_external_apis/lib/form_generation/` (gitignored, not committed):
   - `generated-custom-assessment-forms/<identifier>.json`
   - `overlay.yml` (invented group names, flattened subassessments, inferred `enable_when` — re-used and refined on the next run)
   - `<timestamp>_custom_forms.zip` (only with `ZIP=true`) — the JSON files zipped up for transfer

   Prints a summary and exits non-zero if `Hmis::Form::DefinitionValidator` reports errors. CDED existence checks are skipped at this stage; nothing is published yet.

2. **Upload the zip to Secure Files in production**, via the warehouse UI (Account → Secure Files).

3. **On the production server, download it**:

   ```bash
   dcr shell bundle exec rake "secure_files:download_from_secure_files[<timestamp>_custom_forms.zip]"
   ```

   Lands at `var/<timestamp>_custom_forms.zip`.

4. **Publish it** — dry-run first to see what would happen, with nothing written:

   ```bash
   # preview
   dcr shell bundle exec rails driver:hmis_external_apis:load_custom_assessment_forms ZIP_PATH=var/<timestamp>_custom_forms.zip DRY_RUN=true

   # publish for real
   dcr shell bundle exec rails driver:hmis_external_apis:load_custom_assessment_forms ZIP_PATH=var/<timestamp>_custom_forms.zip

   # one form
   dcr shell bundle exec rails driver:hmis_external_apis:load_custom_assessment_forms ZIP_PATH=var/<timestamp>_custom_forms.zip ONLY=form_identifier_xyz
   ```

   This publishes every form directly — there is no draft step, and CDEDs are minted immediately. Form rules are not created; the form will not appear under New Assessment until a rule exists.

   If you already have an extracted directory of JSON files instead of a zip, pass `DIR=/path/to/dir` instead of `ZIP_PATH`.

## Customer admin review (after the initial publish)

Once a form is published and its CDEDs exist, customer admins edit it directly in production: they create a new draft in Form Builder (reorder, relabel, hide questions, etc.) and publish that draft themselves through the UI. This tool is not involved in that step.

Tell them: change how the form looks and behaves; do not change how answers are stored.

### Safe

- Reorder questions and groups
- Rename labels, helper text, and group titles
- Hide a question they do not want shown (`hidden`). The mapping stays, so migrated answers still have a CDED and can be unhidden later
- Add `enable_when` / required / bounds
- Add a **new** question that is HMIS-only (no legacy-system source). Publishing will mint a new CDED; it will not receive migrated data
- Create next draft, then Publish. That is the Form Builder lifecycle for this work
- Changing pick list options is fine, if you want future data collection to have different options. The migrated values will still be shown as-is even if they are no longer an option in the dropdown.

### Not safe (things that non-super-admins can actually do)

- **Delete a question they still need in HMIS**, even if they do not want it on the form. Delete drops the mapping from the JSON. Publishing only creates CDEDs from mappings that are still on the form, so that legacy-system field has no destination. **Hide instead of delete.** Delete only if the field should not exist in HMIS at all (no migration)
- **Delete and re-add** the same question. The new item has no `custom_field_key`; the next publish creates a different CDED. Old key (and migrated data) are orphaned

## Re-running this tool

Only re-run the generate + publish steps if you found a bug in generation and need to re-create the published forms from scratch — for example, before any customer has started editing them. Read this section fully before you do; re-running is destructive to anything done in Form Builder since the last run.

Publishing an identifier that already has a published version **retires the old published version and publishes a new one** (version + 1) from the freshly generated JSON. It does not merge with or preserve whatever is currently published — if a customer admin has already published their own edits (reordering, relabeling, new questions) for that identifier, **re-running this tool discards those edits.** There is no way to recover a retired version's edits through this tool.

If a customer has an in-progress **draft** for an identifier (created in Form Builder, not yet published), publishing that identifier again deletes the draft first. In `DRY_RUN=true`, existing drafts are only reported, not deleted — always dry-run before a re-run so you know what you are about to discard:

```bash
dcr shell bundle exec rails driver:hmis_external_apis:load_custom_assessment_forms ZIP_PATH=var/<timestamp>_custom_forms.zip DRY_RUN=true
```

CDEDs are keyed by the legacy `custom_field_key` in the CSV, which is stable across runs, so re-generating and re-publishing reuses the same CDEDs (and therefore the same migrated data linkage) rather than creating duplicates — as long as the CSV `key` values themselves haven't changed.

Replace or update the source CSV and re-run generate with the new `CSV_PATH` to pick up a fix:

- Generated JSON is rewritten from the CSV plus overlay.
- Existing overlay keys win (renamed invented groups, hand-edited `enable_when`, `item_order`).
- New identifiers / ungrouped runs / inferred `enable_when` are appended to the overlay.

To suppress an inferred condition, set that `link_id` under `forms.<identifier>.enable_when` to `{}` or `[]`.

## Overlay

```yaml
forms:
  example_form:
    invented_group_names:
      ungrouped_0: Additional Questions
    flattened_subassessments:
      - Client Notes subassessment
    enable_when:
      ifotherdescribe:
        enable_behavior: ALL
        enable_when:
          - question: some_choice
            operator: EQUAL
            answer_code: Other
    item_order:
      VI-FSPDAT v2.0:
        vifspdat2_scoringtotal:
          after: vifspdat2_scoringsectione
      VI-SPDAT v2.0:
        vispdat2_scoringtotal:
          after: vispdat2_scoringsectiond
```
