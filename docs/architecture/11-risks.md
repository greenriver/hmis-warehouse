# 11 Risks and Technical Debts

[← Previous: 10 Quality Requirements](10-quality.md) | [Table of Contents](README.md) | [Next: 12 Glossary →](12-glossary.md)

This section lists identified architectural risks and technical debts, ordered by priority.

## 11.1 Technical Risks

| # | Risk | Impact | Mitigation |
| --- | --- | --- | --- |
| R-1 | **CAS direct database coupling.** The legacy CAS application bypasses the Warehouse API and connects directly to the Warehouse database. | Schema changes in the Warehouse can break CAS without warning. Shared-database integration makes it difficult to reason about data ownership, enforce access controls, or evolve either system independently. Match generation also sits outside this repository, so which clients CAS considered and did not match is not accountable from the warehouse (Q-26 covers declines only). | Planned consolidation of CAS matching functionality into the modern Warehouse Coordinated Entry module. See [5.2.2 CAS](05-building-blocks/05-2-2-cas.md). |
| R-2 | **HUD compliance deadline pressure.** HUD publishes Data Standards and reporting specification updates that must be implemented by fixed deadlines. | Late compliance risks federal funding for CoC partners. The monolith's size can slow implementation of cross-cutting standards changes. | The driver module pattern isolates report implementations. HUD CSV 1:1 source tables reduce the surface area of schema changes. Data-driven form definitions allow collection changes via configuration. |
| R-3 | **Deduplication accuracy.** Cross-source fuzzy matching is inherently imperfect. | False positives (merging distinct clients) corrupt client records. False negatives (failing to link the same client) fragment service history and undermine reporting accuracy. | Deduplication links are maintained separately from source records, so false positives can be unlinked without data loss. Source records are always preserved. Manual review workflows support correction. |
| R-4 | **Upstream data quality.** The platform preserves data from external HMIS sources as-is to provide transparency into data quality issues at their source. | HMIS Leads must understand that DQ issues in reports may originate from upstream systems, not the platform itself. | DQ dashboards give HMIS Leads visibility into upstream issues. Data collected directly through the platform is validated at the point of entry. See [2.3 Conventions](02-constraints.md). |
| R-5 | **Dynamic language runtime.** The Warehouse is built in Ruby on Rails, which lacks static typing and has higher per-request overhead than compiled alternatives. | Type-related defects may not surface until runtime. CPU-bound operations (reporting, deduplication) can be slower than in statically typed or compiled languages. | Actively expanding automated test coverage (including AI-assisted test generation) to catch defects earlier. Performance-critical paths use background processing to avoid impacting interactive response times. The driver module pattern keeps the test surface manageable. |
| R-6 | **Historical data storage growth.** The source-preserving warehouse retains all ingested data across data sources, and time-series records (enrollments, services, assessments) accumulate indefinitely. | Database storage requirements grow with each import cycle. Large tables impact query performance for reporting and deduplication. | Actively pursuing archival of historical data to S3, reducing storage requirements for aged records while preserving access for auditing and compliance. |

## 11.2 Technical Debts

| # | Debt | Impact | Status |
| --- | --- | --- | --- |
| D-1 | **Devise-based local authentication.** Most deployments still manage user accounts locally via the Devise gem rather than through the target SSO architecture (Keycloak / Dex / OAuth2-Proxy). | Security posture varies across deployments depending on which authentication path is active. The target architecture described in [5.2.3 Authentication](05-building-blocks/05-2-3-authentication.md) cannot be fully enforced until migration is complete. | In progress. A long-running feature branch removes Devise entirely in favor of SSO. Deployments are migrated individually as the required infrastructure (auth proxy, IDP services) is provisioned per customer. |
| D-2 | **No per-batch import rollback.** An import that is normalized into the warehouse cannot be undone as a unit. Per-batch import tracking identifies which records a given import touched, but there is no operation that reverses it. | An administrator who imports the wrong data source or reporting period, and discovers it after normalization, has only a point-in-time database restore — which also discards every unrelated change committed since the import. Bounds what [Goal 4, Availability & Resilience](10-quality.md#101-quality-requirements-overview) can actually promise for operator error, as distinct from infrastructure failure (Q-23). | Not scheduled. Reducing it means a reversible import unit: retain the pre-import state of the affected destination records per batch and expose an operator-invocable undo. |

See the GitHub project board for additional issues labeled as technical debt.

## 11.3 Unresolved Quality Goal Conflicts

The [quality goals](01-introduction.md#12-quality-goals) are ranked so that a conflict between two of them has a defined winner. These three tensions are not settled by that ranking. Until each is adjudicated it is resolved ad hoc, differently by different engineers in different features, which is the risk. Ordered by priority.

| # | Conflict | Consequence while unresolved | Measure |
| --- | --- | --- | --- |
| C-1 | **Client Protection & Fair Access (Goal 3) vs Data Integrity & Auditability (Goal 2).** Provenance wants every fact retained indefinitely so any report figure stays auditable. Privacy wants the minimum PII retained for the minimum time. The source-preserving warehouse currently resolves this silently in favour of retention. | No stated retention or redaction position, so there is no answer to a client erasure request that does not also break an audit trail. Every new data-retaining feature re-decides the question. R-6 addresses the storage cost of retention but not its privacy cost. | ADR stating the retention position: what is retained, for how long, and what is redacted or crypto-shredded rather than deleted when a client's data must be withdrawn. |
| C-2 | **Client Protection & Fair Access (Goal 3) vs Operational Self-Sufficiency (secondary).** Operational Self-Sufficiency puts visibility rules, user groups, and CoC partitioning in the administrative UI so administrators need no developer. That is precisely the configuration surface that can widen access to PII without review or a deployment. A goal outranks a secondary requirement, but nothing at the configuration surface enforces that. | Privacy boundaries are only as strong as the least careful administrator, and a widening change leaves no design-time trace. Q-8 (CoC partitioning) and Q-10 (CoC onboarded via admin UI) are the same surface pulling opposite ways. | ADR stating which access-control changes remain self-service and which require review; whichever it is, configuration changes affecting client visibility should be audited like data access is under Q-9. |
| C-3 | **Extensibility & Local Configuration (Goal 1), internally.** The goal asks for two things at once: HUD standards in production before the compliance deadline (Q-1, Q-2), and new mandates arriving as isolated drivers or configuration without touching core models (Q-3, Q-13, Q-24). A fixed HUD deadline is the standing reason to cut through a driver-module boundary or patch a core model directly. Both halves sit inside one goal, so the priority ranking cannot adjudicate between them. | Deadline-driven shortcuts accumulate in the core, eroding the boundaries the second half of the goal depends on. The mitigation under R-2 assumes those boundaries hold. | Accept that the deadline wins, but make the cost visible: record each compliance-driven boundary violation as technical debt in 11.2 at the time it ships, rather than reconstructing it later. |

Resolving any of these means adding an ADR under [Section 9](09-decisions.md); the conflict then moves out of this list and the decision, its rejected alternative, and its date live there instead.
