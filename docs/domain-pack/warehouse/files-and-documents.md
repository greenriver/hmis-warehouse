## Purpose

The `files` table is a single-table-inheritance table with base class `GrdaWarehouse::File`
(`app/models/grda_warehouse/file.rb`), which only declares `acts_as_paranoid` and an optional
`user`. Every subclass adds its own `has_one_attached` ActiveStorage attachment. The subclasses:

- `GrdaWarehouse::ClientFile`: warehouse client document uploads (consent forms, housing
  releases, homeless and disability verifications, headshots, auto-generated service history
  PDFs). The main subject of this doc.
- `Hmis::File` (`drivers/hmis/app/models/hmis/file.rb`): HMIS front-end client uploads. Same
  table, same `ClientFileBase` concern, different associations and visibility scope.
- `GrdaWarehouse::PublicFile`: admin-managed blank forms and templates linked from the files
  tab and the ROI PDF.
- `GrdaWarehouse::ReportResultFile`: LSA zip output, referenced from `ReportResult#file` and
  `#support_file`.
- `GrdaWarehouse::DashboardExportFile`: referenced only by `GrdaWarehouse::DashboardExportReport
  belongs_to :file`; no controller or job writes it.
- `TxClientReports::ResearchExports::Export`: research export output for the TX driver.

Behavior on a `ClientFile` is driven by tags. Tags are `ActsAsTaggableOn` tags whose names
match rows in `GrdaWarehouse::AvailableFileTag`; the boolean flags on that row (consent form,
full release, verified homeless history, notification trigger, document ready, CE self-report
certification, required dates) decide what uploading the file does.

Two file-like models live outside the `files` table and are covered here because agents
reach for them together: `GrdaWarehouse::SecureFile` (user-to-user transfer with a one-month
expiry, table `secure_files`) and `GrdaWarehouse::DocumentExport` (asynchronous report
downloads, table `document_exports`, bytes in a `file_data` bytea column).

Consent behavior (how a consent-tagged `ClientFile` writes `housing_release_status` and the
other consent columns onto the client) is documented in `roi/consent-records.md` and is only
pointed at from here.

## Entry points

- `Clients::FilesController` (`app/controllers/clients/files_controller.rb`): the client
  files tab. `index` splits consent files (`consent_scope`) from other files (`file_scope`,
  which is `non_consent.non_cache`) and lists soft-deleted files via `only_deleted`. Actions:
  `new`, `create`, `show` (download), `update`, `show_delete_modal`, `destroy`, `preview`,
  `thumb`, `batch_download` (zip). Guarded by `require_window_file_access!`, generated by
  `LegacyControllerAuthorization` from `UserPermissions#window_file_access`
  (`can_see_own_file_uploads?`, `can_manage_window_client_files?`, or
  `can_generate_homeless_verification_pdfs?`).
- `Clients::ReleasesController` (`app/controllers/clients/releases_controller.rb`) inherits
  from `FilesController`, skips the window guard, requires `can_use_separated_consent`, and
  limits tags to the `Release of Information` group. `pre_populated` renders a blank ROI PDF
  with Grover, embedding the `client/releases/coc_map` public file.
- `Admin::AvailableFileTagsController`: CRUD for tag rows and their flags, behind
  `require_can_manage_config!`. The rake task `grda_warehouse:seed_file_types` seeds
  `AvailableFileTag.default_document_types` (`app/models/concerns/default_file_types.rb`) and
  the matching `ActsAsTaggableOn::Tag` rows.
- `Admin::PublicFilesController` (`create`, `destroy`) and `PublicFilesController#show`
  (download by id). `PublicFile.url_for_location(name)` resolves the newest public file with
  that exact `name`.
- `SecureFilesController` (`app/controllers/secure_files_controller.rb`): Received, Sent, and
  admin-only All Files tabs; `create` writes one `SecureFile` per recipient in a transaction.
  The developer rake task `secure_files:upload_to_secure_files[filepath,user_id]`
  (`lib/tasks/secure_files.rake`) attaches a local file to your own account.
- Programmatic writers: `ClientHistory` (`app/models/client_history.rb`) creates a
  `ClientFile` tagged `Homeless Verification` from the generated service history PDF;
  `ClientImageConsumer` (`app/models/concerns/client_image_consumer.rb`) writes and
  hard-deletes `Client Headshot Cache` rows and reads files tagged `Client Headshot`.
- `DocumentExportsController` (via `DocumentExportsControllerBase`): JSON `create`, `show`
  (poll), `download`. New export classes must be added to `valid_document_export_classes`.
- Maintenance: `PurgeSoftDeletedClientFilesJob` runs from its own daily cron rake task
  (`grda_warehouse:purge_soft_deleted_records`); `ClientFile.maintain_urls` is enqueued from the
  scheduled `grda_warehouse:every_four_hours` rake task; `SecureFile.clean_expired` runs daily
  via `grda_warehouse:secure_files:clean_expired`; `PruneDocumentExportsJob` deletes exports
  older than 30 days.

## How it works

### STI hierarchy and shared concern

`GrdaWarehouse::File` is deliberately thin: `acts_as_paranoid` plus `belongs_to :user,
optional: true`. Columns on `files` used by the client subclasses include `client_id`,
`enrollment_id`, `data_source_id`, `vispdat_id`, `name`, `note`, `visible_in_window`,
`confidential`, `effective_date`, `expiration_date`, the consent columns
(`consent_form_signed_on`, `consent_form_confirmed`, `consent_revoked_at`,
`consent_revoked_by_user_id`, `coc_codes` jsonb), `delete_reason`, `delete_detail`, and
`active_storage_url`. Legacy columns `file`, `content_type`, `content` (bytea), and `size`
remain from pre-ActiveStorage storage.

`ClientFileBase` (`app/models/concerns/client_file_base.rb`) is included by both
`GrdaWarehouse::ClientFile` and `Hmis::File`. It declares `has_one_attached :client_file,
dependent: false`, PII attributes (`note`, `name`, `client_file`), `soft_delete` and
`soft_delete!` (an `update(deleted_at:)` that avoids `destroy` callbacks), presence of `name`
when a file is attached, `file_exists_and_not_too_large` (100 bytes to 4 MB), `note_if_other`
(a note is required when the `Other` tag is chosen), scopes `newest_first`, `non_cache`
(excludes `name = 'Client Headshot Cache'`), `client_photos` (taggings for
`headshot_tag_name`, `Client Headshot`), `tags` (the matching `AvailableFileTag` rows),
`available_tags` (grouped), and `as_preview` / `as_thumb` (ActiveStorage variants resized to
1920x1080 and 400x400, `nil` on `ActiveStorage::FileNotFoundError`).

`GrdaWarehouse::ClientFile` adds `has_paper_trail`, `acts_as_taggable`, associations to
`GrdaWarehouse::Hud::Client`, `Vispdat::Base`, `Hud::Enrollment`, `DataSource`, and the
revoking user; validation contexts `requires_effective_date`, `requires_expiration_date`, and
`requires_expiration_and_effective_dates` (the controller picks one from the tag flags because
Rails cannot pass two contexts); a rule that a `confidential` file needs either
`data_source_id` or `enrollment_id`; and its own `file_exists_and_not_too_large` that raises
the limit to 12 MB.

`Hmis::File` uses `Hmis::Hud::Client` and `Hmis::Hud::Enrollment`, `Hmis::User` for `user` and
`updated_by`, `has_one :custom_data_element` (a file-valued custom data element), paper_trail
metadata with `enrollment_id`, `client_id`, `project_id`, and stubs `data_source_id` so shared
warehouse code can call it. Its `viewable_by(user, client_ids:)` scope resolves through
`Hmis::Hud::Client.files_viewable_by` and `Hmis::Hud::Enrollment.files_viewable_by`, plus own
uploads when the `can_manage_own_client_files` HMIS permission is held.

The output subclasses (`ReportResultFile`, `DashboardExportFile`, `PublicFile`,
`ResearchExports::Export`) each define `file_data`: download the attachment if attached,
otherwise return the legacy `content` bytes.

### Tags and their effects

`acts_as_taggable` stores `ActsAsTaggableOn::Tagging` rows with `taggable_type =
'GrdaWarehouse::File'` (the STI base class), so tag lookups work across subclasses.
`GrdaWarehouse::AvailableFileTag` (`app/models/grda_warehouse/available_file_tag.rb`) holds
one row per selectable tag name, `belongs_to :tag` by `name`, and is ordered by `group`,
`weight`, `name`. Its columns drive behavior:

- `consent_form`, `full_release`, `coc_available`: the file is a consent form; uploading or
  confirming it writes consent onto the destination client. See `roi/consent-records.md` for
  the full flow (`ClientFile#set_client_consent`, `consent_type`, `calculated_expiration_date`).
- `verified_homeless_history`: the `ClientFile.verified_homeless_history` scope, used by
  `visible_by?` together with `GrdaWarehouse::Config` `verified_homeless_history_visible_to_all`
  and `verified_homeless_history_method` (`:release` restricts to clients with confirmed
  consent in the viewer's CoCs).
- `notification_trigger`: `ClientFile#notify_users` (an `after_create_commit`) sends
  `FileNotificationMailer.notify(client_id)` when
  `AvailableFileTag.should_send_notifications?(tag_list)`. Independently, `NotifyUser.file_uploaded`
  goes out when the client has a valid release and the file is `visible_in_window`.
- `document_ready`: the `document_ready` scope feeds the required-documents checklist views;
  `required_for` (only `veteran` is offered by `available_required_for_options`) makes
  `required_by?(client)` conditional.
- `requires_effective_date`, `requires_expiration_date`: `Clients::FilesController#create`
  selects the matching validation context.
- `ce_self_report_certification`: `ClientFile.recent_ce_self_report_certification`, files with
  `effective_date` in the last year.
- `included_info`: a comma-separated list; `AvailableFileTag.tag_includes('Verification of
  Disability')` powers `ClientFile.verification_of_disability` and the CAS
  `disability_verified_on` sync.

The consent, verified-homeless-history, and CE-certification scopes query `Tagging` ids
directly and cache them for two minutes rather than using `tagged_with`, because `tagged_with`
misbehaves in tests. `ClientFile#tag_list` still comes from `acts_as_taggable`.

After a file is created or destroyed, `Clients::FilesController` calls
`@client.sync_cas_attributes_with_files`, which (when `cas_flag_method` is `file`) sets
`ha_eligible` and `disability_verified_on` from tags.

### Visibility and access

`ClientFile.visible_by?(user)` is the single visibility scope for warehouse files and every
`Clients::FilesController` scope starts from it. `can_manage_client_files?` sees everything.
Otherwise the SQL is built up from: the user's own uploads; all verified homeless histories
when `verified_homeless_history_visible_to_all`; all consent forms when
`consent_visible_to_all`; and, for `can_manage_window_client_files?`, files of clients with a
full housing release (`Hud::Client.full_housing_release_on_file`), restricted to
`visible_in_window` rows and, under `verified_homeless_history_method == :release`, to
verified histories for clients consented in the user's CoCs. `can_see_own_file_uploads?` and
`can_use_separated_consent?` see only their own uploads; `can_generate_homeless_verification_pdfs?`
sees verified histories (own, or all when the config allows).

`visible_in_window` is set at upload (`window_visible?` defaults it to true when absent) and
the controller appends `.window` unless the user `can_manage_client_files?`.

`confidential` files are a second axis: `ClientFile.confidential_visible_by(user)` requires
`can_see_confidential_files` and matches by enrollment project or, for files without an
enrollment, by `data_source_id` of viewable projects. `index` exposes the ids as
`@visible_confidential_ids`; the base `visible_by?` scope does not filter on `confidential`.

`editable_by?` (scope and instance method) allows all for `can_manage_client_files?` and own
uploads for `can_manage_window_client_files?` or `can_see_own_file_uploads?`. `destroy` and
`show_delete_modal` use `editable_scope`.

`create` strips `consent_form_confirmed` unless `can_confirm_housing_release?`, or sets it
when the `auto_confirm_consent` config is on; `update` additionally allows
`can_manage_client_files?` without the confirm flag and revokes consent through
`invalidate_consent!` when `consent_revoked_at` is set on the active consent form.

### Storage, soft delete, and purge

Every current write goes through ActiveStorage. The service is chosen per environment:
`:amazon` (S3) in production and staging, `ENV['ACTIVE_STORAGE_SERVICE']` defaulting to
`:minio` in development, and `:test` (local disk under `tmp/storage`) in tests
(`config/storage.yml`). The `amazon` bucket defaults to
`#{AWS_CLIENT_NAME}-#{AWS_APP_NAME}-#{Rails.env}-files` unless `ACTIVE_STORAGE_BUCKET` is set.
Nothing writes the legacy `content` bytea column any more; the `file_data` fallbacks read it
for historical rows.

`Clients::FilesController#download`, `preview`, and `thumb` stream through `send_data`;
`preview` and `thumb` set a restrictive `Content-Security-Policy` header and honor `stale?`
caching on the file's `updated_at`. `batch_download` builds a zip in memory with
`Zip::OutputStream` named `<client_id>_files.zip`, one entry per file named from its tags.

`ClientFile#active_storage_url` caches the blob URL for external analytics.
`before_save :clear_active_storage_url` nulls it when the service is `:amazon` or `:minio`;
`ClientFile.maintain_urls` back-fills missing URLs in batches with `upsert_all` and is
enqueued (delayed) from the `grda_warehouse:every_four_hours` rake task.

Deletion is soft. `has_one_attached :client_file, dependent: false` stops `acts_as_paranoid`
from enqueuing `ActiveStorage::PurgeJob`, and `soft_delete!` (an `update!(deleted_at:)`)
avoids `destroy` callbacks that would let `acts_as_taggable` hard-delete the taggings, which
would make restore impossible. `Clients::FilesController#destroy` records `delete_reason`
(0 Incomplete Form, 1 Incorrect Client, 2 Incorrectly Categorized, 99 Other) and
`delete_detail` first, then calls `soft_delete!`, `invalidate_consent!` when the file was the
active consent form, `clear_view_cache`, and `sync_cas_attributes_with_files`.

`PurgeSoftDeletedClientFilesJob` (`app/jobs/purge_soft_deleted_client_files_job.rb`) is the
counterpart: under an advisory lock, wrapped in `instrument_as_maintenance_task(name: 'purge')`,
it takes `ClientFile.only_deleted` rows older than `SoftDeleteRetentionConfiguration#retain_at`,
purges each blob, and `really_destroy!`s the row. `SoftDeleteRetentionConfiguration` reads
`AppConfigProperty` keys `purge_soft_deleted_records/enabled`, `retention_period_days` (default
365), and `max_deleted_per_run`; purging is enabled by default only in staging. A disabled
config still completes the maintenance-task run, doing no purging. The job runs from its own
daily cron rake task, `grda_warehouse:purge_soft_deleted_records`.

Content checks are size and type only: `ClientFileBase` enforces 100 bytes to 4 MB (12 MB on
`GrdaWarehouse::ClientFile`), and `PublicFile#content_type_allowed` checks the blob content
type ActiveStorage detected from the bytes against `ALLOWED_CONTENT_TYPES`. There is no virus
scanning in the codebase.

### Public files, secure files, and exports

`GrdaWarehouse::PublicFile` rows are uploaded by admins (`Admin::PublicFilesController#create`
attaches `public_file`, then copies `detected_content_type` into `content_type` so the stored
type comes from the bytes, not the browser). `PublicFile.known_locations` maps well-known
`name` values to display titles: `client/hmis_consent`,
`client/chronic_homelessness_verification`, `client/disability_verification`,
`client/releases/coc_map`. `Clients::FilesController#index` and `ReleasesController#index`
build the blank-form links from `known_hmis_locations` through `url_for_location`, which
returns `public_file_path(id)` for the newest row with that exact name, or `nil`.
`PublicFilesController#show` sends `file_data`.

`GrdaWarehouse::SecureFile` (`app/models/grda_warehouse/secure_file.rb`) is not in the `files`
table. It has `sender`, `recipient`, `name`, `has_one_attached :secure_file`, and
`acts_as_paranoid`. `viewable_by(user)` returns everything for `can_view_all_secure_uploads?`,
rows sent to or by the user for `can_view_assigned_secure_uploads?`, else none, always
intersected with `unexpired` (`created_at` within one month). `received_by(user)` requires
`can_view_some_secure_files?`. `SecureFile.clean_expired` soft-deletes rows older than a
month with `update_all` and runs daily from the scheduled
`grda_warehouse:secure_files:clean_expired` task. The `secure_files:upload_to_secure_files`
rake task refuses recipients whose email does not contain `greenriver` outside development.

`GrdaWarehouse::DocumentExport` (`app/models/grda_warehouse/document_export.rb`) is a
separate STI table, `document_exports`, for asynchronous downloads. `DocumentExportBehavior`
supplies statuses (`pending`, `completed`, `error`), allowed `MIME_TYPES` (binary, PDF,
xlsx), `EXPIRES_AFTER = 30.days`, `CURRENT_VERSION`, `with_status_progression`, `pdf_file=`,
and `diet_select` (all columns except `file_data`). `DocumentExportsControllerBase#create`
requires `type` to be listed in `valid_document_export_classes`, reuses a `completed` export
for the same `type` and `query_string` created within 8 hours (`recent`) unless the subclass
answers `regenerate?` true, otherwise saves a pending row and enqueues `DocumentExportJob`.
`download` checks the subclass's `authorized?` and `completed?` before `send_data`.
`PruneDocumentExportsJob` destroys `expired` rows under an advisory lock. Bytes live in the
`file_data` bytea column, not ActiveStorage.

## Gotchas

- Size limits differ by subclass: `ClientFileBase` allows 100 bytes to 4 MB, which is what
  `Hmis::File` and `PublicFile` enforce; `GrdaWarehouse::ClientFile` redefines
  `file_exists_and_not_too_large` to 12 MB. The 100-byte minimum rejects near-empty uploads.
- `ClientFile#callbacks_skipped = true` disables `notify_users`, `adjust_consent_date`,
  `note_changes_in_consent`, and `set_client_consent`. Bulk writers that set it leave client
  consent columns stale.
- Taggings are stored with `taggable_type = 'GrdaWarehouse::File'`. Direct `Tagging` queries
  must filter on the base class name, not the subclass.
- The consent, verified-homeless-history, and CE-certification scopes cache tagging ids for
  two minutes. `set_client_consent` deletes `CONSENT_FORM_TAG_CACHE_KEY` first, but a tag
  change on an `AvailableFileTag` row is not reflected until the cache expires.
- `visible_by?` does not filter `confidential`. Views decide what to show from
  `@visible_confidential_ids`; a new endpoint that serves file bytes must apply
  `confidential_visible_by` itself.
- `Clients::FilesController#create` rescues `StandardError` and re-renders `new` with no flash,
  so a failed save shows only model errors; a raised exception elsewhere in the block is
  swallowed. `destroy` rescues `Exception`. Both predate the no-bare-rescue convention.
- `PurgeSoftDeletedClientFilesJob` still runs (and completes its maintenance-task tracking)
  when `purge_soft_deleted_records/enabled` is unset outside staging, but does no purging.
  Soft-deleted files and their blobs otherwise persist indefinitely.
- `Admin::PublicFilesController#destroy` calls `destroy`, not `soft_delete!`. `PublicFile` is
  paranoid and taggable, so its taggings are hard-deleted on soft delete.
- `ClientImageConsumer` hard-deletes `Client Headshot Cache` rows with `really_destroy!` after
  purging the blob, under a per-client advisory lock; those rows are excluded by name by
  `non_cache` and skipped by `notify_users`.
- `PublicFile.url_for_location` matches `name` exactly. An admin must upload with the literal
  key (for example `client/hmis_consent`) or the files tab link silently disappears.
- `ClientFile.maintain_urls` re-raises blob errors outside development; a single missing S3
  object fails the whole batch run.
- `clear_active_storage_url` only runs when the service is `:amazon` or `:minio`, so in test
  the column keeps whatever a factory set.
- `SecureFile.viewable_by` follows the role, not ownership: losing
  `can_view_assigned_secure_uploads` hides a user's own past uploads. `expired` compares
  `created_at` to `1.months.ago.to_date` while `unexpired` uses `1.months.ago`, so rows created
  within the boundary day match neither.
- `DocumentExportsControllerBase#find_or_create` returns a cached completed export within
  8 hours for the same `type` and `query_string`; a subclass whose output depends on time or
  on data outside the query string must return `true` from `regenerate?`.
- `Hmis::File#data_source` returns `nil` and `data_source_id` is a plain accessor, so the
  `ClientFile` confidential validations (`data_source` or `enrollment` required) do not exist
  on HMIS files.

## Do not repeat

- Storing client documents in a new table or a new `has_one_attached` on some other model.
  Add a subclass of `GrdaWarehouse::File` with `has_one_attached ..., dependent: false` and a
  `file_data` fallback, as `GrdaWarehouse::ReportResultFile`
  (`app/models/grda_warehouse/report_result_file.rb`) does. `GrdaWarehouse::SecureFile` is the
  deliberate exception because it is user-to-user, not client-bound.
- Hard-coding tag names in application code. Existing offenders:
  `app/models/client_history.rb:80` (`'Homeless Verification'`),
  `app/models/concerns/cas_client_data.rb:674-681` (`'BHA Eligibility'`,
  `'Housing Authority Eligibility'`, `'Limited CAS Release'`), and
  `app/models/concerns/client_image_consumer.rb:127` (`'Client Headshot'`). Use the
  `AvailableFileTag` flag scopes (`verified_homeless_history`, `consent_forms`,
  `tag_includes(...)`) or the shared constant `ClientFileBase.headshot_tag_name`. Views already
  render `file.tag_list` against `@available_tags` (`app/views/clients/files/_file_row.haml:10-13`)
  rather than naming tags.
- Deleting a `ClientFile` or `Hmis::File` with `destroy`. Use `soft_delete!`; `destroy` hard
  deletes the taggings and blocks restore. `Clients::FilesController#destroy`
  (`app/controllers/clients/files_controller.rb`) is the model.
- Writing bytes to the legacy `content` bytea column or reading `file` / `content_type` as if
  they were current. Attach through ActiveStorage; read through `client_file` or the
  subclass's `file_data`.
- Using `tagged_with` inside a scope that must be correct under RSpec for consent or
  verified-homeless-history lookups. Follow `ClientFile.consent_forms`
  (`app/models/grda_warehouse/client_file.rb`): resolve `Tagging` ids and `where(id:)`.
- Adding a `DocumentExport` subclass without registering it in
  `DocumentExportsControllerBase#valid_document_export_classes`
  (`app/controllers/document_exports_controller_base.rb`); `create` rejects unlisted types with
  `ActionController::BadRequest`.
- Writing consent columns on the client from a new file path. The only writers are listed in
  `roi/consent-records.md`.
